## 一、相关技术仔细分解（按面试可讲深度分层）

### 1. 后端框架与工程基础
- **Python 3.11 + FastAPI + Uvicorn**：全异步服务
- **Pydantic v2 / pydantic-settings**：接口数据校验 + 类型安全配置
- 中间件链路：**request_id 链路追踪**、CORS、统一异常处理与响应 envelope（`ok()`）
- `GET /api/health` 存活探针（可讲：验收门槛「项目可启动」的自动化探针）

### 2. 数据层
- **SQLAlchemy 2.0 ORM + MySQL 8**（PyMySQL / aiomysql，cryptography 处理 caching_sha2_password 认证）
- 测试环境用 **aiosqlite** 隔离，不依赖真实 MySQL
- **编号式 SQL 迁移**（005 token/短信/支付、006 账本单位「分→元」）+ 数据回填脚本（backfill_task_tokens / migrate_ledger_to_yuan）

### 3. 多模型供应商网关（核心架构亮点）
- **适配器模式**：`providers/base.py` 统一抽象接口 → DashScope（阿里云百炼）/ OpenAI 兼容 / SiliconFlow（硅基流动）/ Mock 各自实现
- **httpx 异步调用**上游；任务统一建模（`ai_task`：文本/文生图/语音/视频）
- **Mock 供应商**支撑无 Key 全链路联调；新增模型只注册配置、不改业务代码（开闭原则）

### 4. 计费与资金安全（最有含金量的业务设计）
- **统一计价服务 pricing**：按模型/媒体类型定价，与业务解耦
- **钱包「冻结—结算—退款」三态流转**（cost_status: frozen / settled / refunded），核心不变量：**失败绝不扣费**
- **启动补偿（crash-safe）**：进程重启丢失后台任务收尾时，扫描滞留冻结资金自动退回
- **支付宝充值集成**、消费记录流水、账本单位迁移（分→元）

### 5. 认证与安全
- **JWT + token 黑名单**（登出/吊销即时生效）
- **短信验证码登录**（阿里云 SMS，RAM 子账号最小授权 AliyunDysmsFullAccess）
- **API Key 签发校验 + 限流**（单 Key 每分钟调用上限）

### 6. 前端（理解即可，不必深讲）
- 原生 HTML/JS/CSS 多页面：chat / image / video / audio / models / pay / auth / profile
- `api.js` 统一封装（token 注入、错误处理）、模型切换、支付页

### 7. 质量保障与团队协作
- **pytest + pytest-asyncio**：计费计价、认证、支付、短信、API Key、媒体 provider 均有测试
- **Git worktree 多分支并行开发**（test1 → master 合流）、约定式提交、团队工作包（WP）分工交付

## 三、面试官可能追问的点（提前备好答案）

1. **「冻结—结算—退款」怎么保证并发安全？** → 钱包余额变更走数据库事务 + 行锁（`SELECT ... FOR UPDATE`），冻结/结算/退款都在同一事务内落流水。
2. **启动补偿为什么必要？** → 后台任务收尾在内存中，进程重启会丢失；扫描 `status in (pending, processing) and cost_status=frozen` 的任务退回冻结额，保证「失败绝不扣费」在重启场景同样成立。
3. **新增一个供应商要改多少代码？** → 继承 base 抽象实现 fetch/submit/query，注册配置即可，业务层零改动（开闭原则）。
4. **token 黑名单怎么实现？** → 登出/吊销时写入黑名单表，鉴权中间件先查黑名单再验签，TTL 与 token 剩余有效期对齐。
5. **为什么用编号式 SQL 迁移而不是 Alembic？** → 迁移含数据订正（单位分→元、token 回填），需要显式控制执行顺序和幂等，编号脚本 + 执行记录表更直观可控。
